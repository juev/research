## Аннотация

Structured output у локальной модели полезно понимать как четыре разных контракта: синтаксис JSON, соответствие экземпляра JSON Schema, язык, реально допускаемый сгенерированной грамматикой, и смысловую правильность ответа. Совпадение первых двух уровней само по себе не гарантирует ни третий, ни четвёртый. Данные и версии зафиксированы на 2026-11-26; обзор опирается на RFC 8259, спецификацию JSON Schema 2020-12, исходный код и тесты llama.cpp v1.0.0 и Ollama v0.40.17, выпуски, открытые issue и шесть исследований constrained decoding.[^1][^2][^5][^10][^19]

Главный практический вывод: грамматика должна снимать класс синтаксических сбоев, а не заменять проверку результата. В llama.cpp конвертер сознательно отклоняется от JSON Schema и имеет задокументированные неподдерживаемые конструкции; в Ollama поведение зависит от runner, а сохранённый в tool definition ключ схемы ещё не означает, что он применён к аргументам. Даже полностью валидный JSON может содержать перепутанные значения или неправильно выбранный инструмент. Надёжная схема эксплуатации — компактная схема на входе, независимая валидация на выходе, прикладные проверки и авторизация tool call.[^9][^18][^19][^20][^22]

## Введение

**Актуальность.** В ноябре 2026 года llama.cpp выпустил v1.0.0, а Ollama — v0.40.17. В примечаниях к релизам есть изменения как раз вокруг structured output: llama.cpp исправил `allOf` для простых типов и обработку `response_format` в парсерах, Ollama перестала отбрасывать неизвестные ей ключи JSON Schema в переданных через API определениях инструментов. Это хороший повод проверить не рекламную формулировку «гарантированный JSON», а точную границу гарантии.[^10][^19]

**Цель** — определить, что именно обещают JSON Schema и grammar-constrained decoding, какие несоответствия видны в зафиксированных версиях двух локальных движков и какие проверки обязаны остаться в приложении. Отдельно рассматриваются `response_format`/`format` и tool calling: у них общие механизмы, но разные последствия ошибки.[^8][^13][^20]

**Границы.** Это документарный разбор, а не новый benchmark: скорость генерации, качество конкретных моделей и доля ошибок на пользовательском корпусе здесь не измерялись. Ссылки на issue означают зафиксированное состояние на дату среза, а не вечный дефект; числа из исследований относятся только к их моделям и наборам задач.[^12][^18][^22]

## 1. Четыре слоя вместо одного «valid JSON»

Первый слой — синтаксис сериализации. RFC 8259 определяет JSON как текстовый формат и объект как **неупорядоченный** набор пар «имя — значение»; синтаксически правильный документ ещё ничего не говорит о типах полей и их смысле. Поэтому `{"status":"green"}` и `{"status":"done"}` могут быть одинаково хорошим JSON, хотя для приложения допустимо только одно значение.[^1]

Второй слой — соответствие экземпляра схеме. JSON Schema 2020-12 разделена на Core и Validation: первая описывает структуру схемы, ссылки и dialect, вторая — ключи валидации. Важно, что часть ключей по умолчанию является аннотацией: например, `format` сам по себе не обязан запускать проверку, если реализация или конфигурация не включили соответствующее поведение. Следовательно, даже вызов «JSON Schema validator» нужно уточнять: какой dialect, vocabularies и режим assertion он применяет.[^2][^3]

Третий слой — язык сгенерированной грамматики. Конвертер берёт схему и строит правила допустимых продолжений; во время decoding движок маскирует токены, которые не могут продолжить текущий префикс. XGrammar описывает это как grammar-guided generation с маской токенов, Outlines — как generation по конечному автомату. Это ограничение **процесса выбора токенов**, а не постфактум-проверка готового ответа и не доказательство эквивалентности исходной схеме.[^5][^6]

Четвёртый слой — задача. Поле `animal` со строкой `"blue"` пройдёт схему `{"type":"string"}`, но останется неверным ответом на вопрос о животном. JSONSchemaBench поэтому различает declared coverage, то есть перечисленные разработчиком возможности, и true coverage, измеренную на схемах; для инженерного контракта нужно добавить ещё и прикладную корректность, которую общий benchmark схем не измеряет.[^7][^22]

## 2. Что грамматика реально меняет в decoding

Без ограничения модель на каждом шаге распределяет вероятность по словарю токенов. С грамматикой движок вычисляет допустимое подмножество, обнуляет или сильно понижает остальные логиты и нормализует оставшееся распределение. Пока состояние конечного автомата или стек грамматики отслеживается правильно, недопустимая последовательность не будет выбрана; XGrammar и Outlines решают прежде всего проблему эффективного вычисления таких масок.[^5][^6]

Отсюда следует сильная, но узкая гарантия: снимаются определённые ошибки формы — лишняя запятая, незакрытая скобка, токен вне разрешённой ветки. Не следует гарантия, что выбранная ветка `anyOf` соответствует намерению пользователя, что enum выбран правильно или что текст в свободной строке истинен. Если валидным продолжениям модель назначила мало вероятности, маска перераспределит массу между ними, но не добавит знание.[^5][^22][^24]

Порядок полей показывает скрытую цену такого сжатия пространства. JSON рассматривает ключи объекта как неупорядоченные, а генератор вынужден выдавать их в каком-то порядке. Если грамматика разрешает только один порядок, она сужает язык сильнее схемы; это может быть безопасно для парсера, но менять поведение модели, которая в prompt или в процессе reasoning выбрала другой порядок.[^1][^12][^18]

Поэтому «100% schema-valid» нельзя автоматически переводить как «100% usable». В небольшом исследовании Chavan constrained decoding довёл schema validity пяти моделей размером 0.6B–4B с исходных 78.6–92.9% до 100%, однако часть смысловых ошибок сохранилась, особенно в многошаговом function calling. Это результат одного preprint на 14 задачах, а не универсальная оценка всех локальных моделей, но он корректно разделяет структурную и смысловую метрики.[^22]

## 3. llama.cpp v1.0.0: контракт с явными исключениями

### 3.1. Входные формы и момент запуска

`llama-server` принимает `json_schema`, `response_format` и `grammar`. Для OpenAI-совместимого chat endpoint документация разрешает как `json_object`, так и `json_schema`, включая wrapper с `json_schema.name`, `strict` и `schema`. Это разные способы задать ограничение; наличие поля `strict` во входном wrapper не превращает конвертер в полную реализацию JSON Schema 2020-12.[^8]

Для `/completion` сервер может активировать grammar lazy — после `grammar_trigger_words` или совпадения с trigger pattern — либо применять её сразу. Операционно это важно: если ограничение запускается по триггеру, текст до триггера живёт вне его гарантии, а служебные поля самого API не становятся частью сгенерированного JSON. Проверять нужно именно `content` или аргументы вызова, а не весь HTTP-ответ как единый документ.[^8]

GBNF также не является «другим JSON Schema». В grammars/README проект предупреждает, что GBNF не обладает выразительностью обычных регулярных выражений, не позволяет захватывать группы и не понимает look-ahead/look-behind. `json-schema-to-grammar` — удобный конвертер для пересекающегося подмножества, а не универсальный способ перенести любую схему или regex.[^9]

### 3.2. Неподдерживаемое и намеренно изменённое

Список ограничений v1.0.0 включает `patternProperties`, `uniqueItems`, `contains`/`minContains`, `$anchor`, `not` и условия `if`/`then`/`else`/`dependentSchemas`; есть и ограничения на `$ref`, regex и длину строк. Если приложение рассчитывает на `uniqueItems`, одного прохождения через grammar недостаточно: дубликат может оказаться допустимым для сгенерированного языка, но недопустимым для исходной схемы.[^9]

Отдельный случай — `additionalProperties`. Спецификация и справочник JSON Schema разрешают дополнительные свойства по умолчанию; `false` запрещает их. llama.cpp делает противоположный выбор по умолчанию и формулирует его прямо:[^4][^9]

> The JSON schemas spec states `object`s accept additional properties by default. Since this is slow and seems prone to hallucinations, we default to no additional properties.

Это не обязательно создаёт невалидный ответ: более узкая грамматика может просто отбросить поле, которое исходная схема разрешала. Но две стороны теряют одинаковый язык допустимых документов. Для расширяемых payload нужно явно писать `"additionalProperties": true`, а для строгого контракта — `false`, не полагаясь на разные defaults движка и валидатора.[^4][^9]

### 3.3. Исправленный `allOf` и оставшиеся границы

В v1.0.0 вошёл PR #31834: раньше `allOf` из простых типов мог превращаться в грамматику пустого объекта. Исправление объединяет неструктурные листья и числовые диапазоны, а тест пустого пересечения диапазонов ожидает ошибку. Однако сам merge request фиксирует ограничение: parser не хранит bounds для `number`, поэтому в тесте со схемой `integer` плюс `number` с `minimum: 0` и `maximum: 100` получается **unbounded integer**; диапазон 0–100 не enforced.[^10][^11]

Это особенно показательный пример: закрытый issue и зелёный unit test подтверждают исчезновение конкретного `{}`, но не выполнение всей исходной схемы. Для чисел с бизнес-ограничением независимая проверка обязательна, а там, где возможно, схему лучше заранее нормализовать в простой bounded `integer`, поведение которого покрыто тестом.[^11]

Другой открытый на дату среза issue #30321 описывает optional-поле перед required: правило ставит обязательные ключи вперёд, модель, следующая порядку схемы, блокируется и может опустить optional-поле. В комментариях отдельно отмечено, что order-free правила для tool-call arguments не меняют `response_format`/`--json-schema`. Это репорт и обсуждение, а не проведённое в этом обзоре воспроизведение; практический вывод — тестировать порядок ключей и не толковать JSON-неупорядоченность как свободу конкретной grammar.[^12]

## 4. Ollama v0.40.17: схема проходит через несколько компонентов

### 4.1. Native API, OpenAI compatibility и prompt

Ollama принимает `format: "json"` либо объект JSON Schema в `/api/chat`; в OpenAI-совместимом API используется `response_format`. Документация рекомендует дополнительно включить схему строкой в prompt «to ground the model's response», а примеры не ограничиваются генерацией: результат разбирают через `Country.model_validate_json(...)` или `Country.parse(JSON.parse(...))`. Сам официальный quickstart тем самым показывает правильную границу — grammar плюс независимый parse/validate.[^13][^21]

В runner для llama.cpp функция `llamaServerChatResponseFormat` превращает `"json"` в `{"type":"json_object"}`, а объект схемы — в `json_schema` с именем `schema`. Ошибочный тип входа даёт `invalid format`, то есть API проверяет форму параметра. Но это преобразование конверта запроса не доказывает полноту последующей конвертации схемы в GBNF: последняя остаётся на стороне соответствующего llama.cpp runner.[^14]

Интеграционный тест `TestStructuredOutput` проверяет ожидаемые поля и типы на конкретной модели, а `TestStructuredOutputThinking` отдельно проходит сценарий thinking model. Такие тесты полезны как регрессионный контракт поддерживаемого пути, но не заменяют JSON-Schema-Test-Suite: один успешный ответ не доказывает ни покрытие ключей, ни отклонение всех невалидных экземпляров.[^15][^25]

### 4.2. MLX — другой путь исполнения

В v0.40.17 MLX runner имеет собственный `mlxrunner/grammar.go`: компиляция XGrammar выполняется параллельно остальной инициализации, ошибка компиляции возвращается вызывающей стороне, а при недоступности structured output runner отвечает `501` с `structured output is unavailable`. После компиляции matcher применяет token mask. Значит, поведение нельзя переносить с GGUF/llama.cpp на MLX только потому, что внешний параметр называется одинаково `format`.[^16]

Исторический issue #18567 о бесконечной генерации и тихо игнорируемой схеме на MLX относится к v0.17.5 и был закрыт в сентябре 2026 года; текущий зафиксированный код уже содержит явную ошибку и token masks. Это пример, почему старый воспроизводимый дефект нельзя без проверки кода и релиза переносить на v0.40.17 — равно как и закрытие issue не доказывает поддержку всех ключей JSON Schema.[^16][^17]

### 4.3. Порядок ключей и сохранённые keywords

Открытый issue #18717 показывает другой класс проблемы: на native chat path порядок свойств схемы мог сортироваться по именам, а не сохраняться. В воспроизведении на v0.35.1 модель выдала `{"alpha_animal":"blue","zeta_colour":"zebra"}`: объект валиден, но цвет попал в поле животного. В v0.40.17 `llamaServerChatResponseFormat` по-прежнему разбирает схему в Go `map[string]any`, поэтому порядок нельзя считать переносимой частью контракта; сам issue на 2026-11-26 остаётся открытым.[^14][^18]

Релиз v0.40.17 одновременно сообщает, что tool definitions, переданные через API, сохраняют JSON Schema keywords, которые Ollama не моделирует, вместо их удаления. Сохранение данных и enforcement — разные операции: ключ доехал до runner, но из release note не следует, что `uniqueItems`, условие или `format` реально ограничили аргументы. Их нужно проверять на принимающей стороне.[^19]

## 5. Tool calling добавляет контракт действия

Ollama описывает tool calling как цикл: приложение передаёт tools и messages, получает вызов с именем и аргументами, выполняет функцию у себя и возвращает результат модели. Даже идеально валидные аргументы не доказывают, что выбрано правильное имя функции, что вызов уместен в текущем состоянии и что его разрешено выполнять этому пользователю. Синтаксический контракт заканчивается до авторизации действия.[^20]

В llama.cpp v1.0.0 есть отдельные исправления chat parsers: учитывать `response_format`, экранировать control characters и очищать invalid UTF-8 в tool arguments. Само наличие этих изменений подтверждает, что путь tool call включает не только grammar, но и chat template, parser и сериализацию. Интеграционный тест должен проверять всю цепочку, а не только автономный конвертер схемы.[^10]

Практическая граница доверия выглядит так: имя инструмента сопоставляется с allowlist, аргументы проходят JSON Schema и прикладную валидацию, идентичность и права проверяются независимо, побочный эффект выполняется только после этих шагов. Для необратимых операций нужен отдельный policy gate; повторная генерация не является контролем безопасности.[^13][^20][^22]

## 6. Смысл, reasoning и противоречивые результаты

Исследования сходятся в пользе структурных ограничений, но не в едином выводе о качестве. Chavan на маленьких открытых моделях получил 100% schema validity при сохранении semantic gap. Tam и соавторы в EMNLP 2024 наблюдали снижение reasoning под format restrictions, причём более строгие ограничения часто ухудшали результат; однако в classification JSON-mode иногда улучшал точность. В их разборе Last Letter порядок `answer` перед `reason` провоцировал direct answer вместо reasoning-first, то есть схема влияла не только на парсинг, но и на стратегию ответа.[^22][^23]

DCCD предлагает другое объяснение и смягчение: сначала создаётся unconstrained draft, затем constrained decoding выполняется с conditioning на него. Авторы называют потерю вероятностной массы на допустимых продолжениях «projection tax» и сообщают о результатах от небольшого снижения до +24 процентных пунктов к baseline в зависимости от режима. Это многообещающий, но отдельный метод с двумя этапами и дополнительной стоимостью; его цифры нельзя приписывать обычному `format` в Ollama или `json_schema` в llama.cpp.[^24]

JSONSchemaBench добавляет второе противоречие — между заявленной и измеренной поддержкой. Работа сравнивает шесть framework и показывает, что списки поддерживаемых ключей не совпадают с поведением на 10 тысячах реальных схем; для полной схемы ещё проверяется соответствие сгенерированного вывода валидатору. Следовательно, документация нужна для определения intended contract, а тесты на собственных схемах — для установления фактического.[^7]

Эти работы не отменяют structured output. Они меняют критерий выбора: для extraction и классификации жёсткая схема часто уместна; для сложного reasoning стоит сравнить прямой constrained режим с двухэтапным «свободный ответ → преобразование в формат», измеряя и validity, и task accuracy на одних входах.[^23][^24]

## 7. Практический контракт для self-hosted пайплайна

**1. Сузить схему до проверенного подмножества.** Убрать необязательную сложность `allOf`, условия, `not`, `patternProperties` и regex без явных anchors; числовые границы и `additionalProperties` писать явно. Для llama.cpp сверять конструкции с limitations v1.0.0, для Ollama — ещё и фиксировать runner и backend. Понятная компактная схема уменьшает не только шанс unsupported keyword, но и число решений, которые грамматика навязывает модели.[^9][^11][^16]

**2. Проверять результат независимым валидатором.** Сначала `JSON.parse` или эквивалент, затем JSON Schema нужного dialect, затем Pydantic/Zod или собственные прикладные правила. Отдельно решить, требуется ли assertion для `format`; проверить диапазоны, уникальность, перекрёстные условия и допустимость дополнительных полей. Официальные примеры Ollama уже используют именно такой второй барьер.[^3][^9][^13]

**3. Тестировать обе стороны языка.** Набор fixtures должен содержать не только валидные примеры, которые модель способна выдать, но и невалидные, которые валидатор обязан отвергнуть: пропущенное required-поле, дубликат при `uniqueItems`, число вне диапазона, неверную ветку `anyOf`, другое количество и порядок ключей. JSON-Schema-Test-Suite полезен как эталон для валидатора, а собственные generation tests — как проверка конкретной связки model/runtime/schema; один не заменяет другой.[^7][^15][^25]

**4. Оценивать смысл и failure policy.** Для каждой задачи хранить ожидаемые значения, а не только ожидаемую форму; отдельно считать parse rate, schema validity, exact/semantic accuracy и unsafe tool-call rate. При ошибке валидации возвращать `422`/доменную ошибку или делать ограниченный repair с новой диагностикой, но не зацикливать одинаковый запрос. Для tool calls любой сомнительный вызов остаётся невыполненным.[^20][^22][^23]

## Дискуссионные вопросы и противоречия

Первое противоречие терминологическое: производитель говорит «enforce a JSON schema», а конвертер документирует исключения и другой default для `additionalProperties`. Корректное прочтение — enforce **поддерживаемое представление** схемы, а не всю семантику JSON Schema 2020-12. Чем сильнее приложение опирается на неподдерживаемый ключ, тем важнее независимый валидатор.[^2][^9][^13]

Второе противоречие эмпирическое: constrained decoding может улучшить классификацию, ухудшить reasoning или оставить смысловую ошибку неизменной. Различия объясняются задачами, моделями, порядком полей и тем, измеряется ли только формат или ещё и ответ. Поэтому переносить единый процент выигрыша между бенчмарками и продукционными схемами нельзя; общий вывод ограничивается необходимостью двухосевой оценки.[^22][^23][^24]

Третье противоречие временное: issue фиксирует дефект, release note — конкретное исправление, а pinned source — фактический код версии. Исторический MLX issue нельзя считать текущим поведением v0.40.17, но закрытый `allOf` issue нельзя считать доказательством полной поддержки числовых bounds. Наиболее надёжный вывод получается только при совместном чтении этих источников.[^11][^16][^17]

## Недостаточность данных

Не измерены latency и memory overhead именно llama.cpp v1.0.0 и Ollama v0.40.17 на одинаковом железе; академические результаты XGrammar и Outlines относятся к их собственным реализациям и экспериментам. Также нет оснований обобщать semantic gap пяти маленьких моделей на все современные GGUF/MLX-модели. Для capacity planning и выбора модели нужен отдельный paired benchmark на собственных prompts, schemas и версиях runner.[^5][^6][^22]

## Заключение

Structured output в llama.cpp и Ollama — полезный механизм устранения структурных сбоев, но его контракт заканчивается на языке конкретной грамматики и конкретного runner. JSON Schema описывает допустимый экземпляр шире и точнее, чем способен выразить ряд конвертеров; прикладная корректность начинается ещё позже. Поэтому правильная единица доверия — не HTTP 200 и не успешный `JSON.parse`, а цепочка «pinned runtime → поддерживаемая схема → независимая валидация → semantic checks → авторизованное действие».[^1][^9][^16][^20]

Для self-hosted систем разумный default такой: версионировать модель, runner и schema вместе; использовать простые схемы; тестировать валидные и невалидные случаи; отдельно измерять точность содержимого; никогда не исполнять tool call только на основании его синтаксической валидности. Грамматика уменьшает пространство ошибок формы — ответственность за смысл и последствия остаётся у приложения.[^7][^20][^22]
